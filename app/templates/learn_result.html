What each parameter does

client_id identifies your application. Public by design.

redirect_uri is where the provider sends the user back. It has to match your registration exactly. Mismatches here are the most common OAuth error there is.

scope is what you are asking permission for. The user sees it on the consent screen.

state is a random CSRF token. Your app stored it and set a matching cookie.

response_type=code selects the Authorization Code flow.

Front channel

Callback received

The provider redirected the browser back with two values.

code{{ debug.callback_code }}
state {{ debug.callback_state }} matched the cookie
The code came through the browser, so treat it as public. On its own it is useless. Redeeming it takes your client secret, which never left your server.
Why the state check matters

The code is short-lived and single-use. It is not an access token.

The state must match what your app sent in step 1, and it must match a value tied to this browser, not merely one the server issued to somebody.

Check only that the state exists server-side and you have a problem. An attacker can start their own login, capture a valid state, then hand the callback URL to someone else. That person's browser redeems it, and they end up signed into the attacker's account. This is login CSRF.

This app binds the state to a cookie set at login, so a state from another browser is rejected.

The session cookie is set here: HttpOnly, so JavaScript cannot read it, and bound to a server-side record that expires on its own.
Why normalize at all

GitHub sends login and avatar_url. Google sends name and picture. The demo provider sends display_name and email_address.

normalize_userinfo() maps all of them onto id, name, email, avatar, so the rest of your app never has to care who signed the user in.

One thing worth remembering: these values are attacker-controlled. A display name can contain HTML. Escape it before rendering, the same as any form field.
