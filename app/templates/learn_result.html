What each parameter does

client_id identifies your application. You got it when you registered with the provider. It is public.

redirect_uri is where the provider sends the user back. It must match what you registered, exactly.

scope is the permissions you are asking for. The user sees these on the consent screen.

state is a random token for CSRF protection. Your app stores it and checks it on the way back.

response_type=code selects the Authorization Code flow — the right choice for server-side apps.

{% if debug.authorize_params.get("code_challenge") %}

code_challenge is the SHA-256 hash of a secret your app just generated. The provider stores it and, in step 3, demands the original. That is PKCE.

{% endif %}

Callback received

Front channel

The provider redirected the browser back to your app with two values.

code {{ debug.callback_code }}
state {{ debug.callback_state }}verified
The code travelled through the browser, so treat it as public. It is useless on its own — redeeming it takes your client secret, which never left your server.
Why the state check matters

The code is short-lived and single-use. It is not an access token.

The state must match what your app sent in step 1 — and it must match a value tied to this browser, not merely one the server issued to someone.

If you only check that the state exists server-side, an attacker can start their own login, capture a valid state, and hand the callback URL to a victim. The victim's browser redeems it and they end up signed into the attacker's account. That is login CSRF.

This app binds the state to a cookie set at login, so a state from another browser is rejected.

The session cookie is set here — HttpOnly, so JavaScript cannot read it, and bound to a server-side record that expires on its own.
Why normalize at all

GitHub sends login and avatar_url. Google sends name and picture. The demo provider sends display_name and email_address.

normalize_userinfo() maps all of them onto id, name, email, avatar, so the rest of your app never has to care which provider signed the user in.

One more thing worth knowing: these values are attacker-controlled. A display name can contain HTML. Escape it before rendering, exactly as you would a form field.
